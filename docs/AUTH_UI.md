# Authentication UI and startup

The executable entry point (`main.dart`) enables `JobTrailApp(showAuthentication: true)`.
Startup uses Splash V2: a native 2.65-second cinematic sequence followed by a 220ms fade to Login/Home (about 2.87 seconds total when session restoration has resolved). `AuthProvider.restoreSession` still gates the destination; a failed or timed-out check stays gated with retry. Reduced motion skips the cinematic sequence and the transition. Session invalidation removes protected content immediately, without a fading Home frame.

`UnavailableAuthProvider` always restores a signed-out state and rejects account operations. There is no account creation, email delivery, OAuth, persistence or real password reset. Provider failures use accessible feedback. Preview-only email/reset states are explicitly marked as development UI and never call the provider. Google Sign-In remains disabled.

Debug builds expose a labeled Home demo bypass. It only changes in-memory UI state and creates no auth session. It is absent in release/profile builds. JobTrailApp defaults to the auth gate. Existing frontend tests explicitly use `showAuthentication: false` to retain isolated shell coverage; this flag is ignored in profile/release, even if a caller explicitly passes false. Application startup keeps the default gate enabled.

A future provider can implement `AuthProvider` and be injected into `JobTrailApp`; sign-in completion is followed by `restoreSession` and only an established session opens Home. Session checks and account requests time out after 10 seconds. Replacing the provider ignores old session results. Password-reset token validation, auth-state subscriptions, logout, revocation, cancellation and clearing protected routes must be designed with that integration. A UI timeout does not cancel a provider-side operation. This UI does not establish a secure backend boundary.
